# 2026-09-06 — bench session 1 (read-only) and V15 analysis

Host: the owner's MacBook (macOS, Python 3.14 from Homebrew, venv with
`crcmod pyyaml mido python-rtmidi`), FM-1 on USB-C directly. Everything below
is **[verified]** on this unit unless marked otherwise. Nothing was written to
the device; the only vendor-family message sent was the identity query.

## 1. USB enumeration (docs/09 §2)

| Field | Value |
| --- | --- |
| VID:PID | `4C4A:C755` (19530:51029) |
| USB | `bcdUSB 0x0200`, **full speed** (12 Mb/s), `bMaxPacketSize0 64`, `bcdDevice 0x0100`, `bDeviceClass 0` |
| Product string | `FM-1` (device level) |
| Serial | 16 hex digits that read as seven ASCII characters plus one byte; probably the chip ID (value kept out of the public repo) |
| Interfaces | 0 audio control (1/1), 1 audio streaming (1/2), 2 audio streaming (1/2), 3 audio control (1/1), 4 **MIDI streaming (1/3)** — a UAC1 function and a USB-MIDI function |
| CoreMIDI | one port `FM-1` (input and output) |
| CoreAudio | device `FM-1 Audio`: 2 output channels, 2 input channels, 44100 Hz, "Unknown Manufacturer" |

**Power switch test (21:27 local):** with the FM-1 on the USB-C cable and the
slide switch off for 20 s, the device is absent from the USB bus: no
`IOUSBHostDevice` node, no CoreMIDI port, no identity reply. Three earlier
monitors (`scratch/usb_monitor*.log`, one sample per second over 15 minutes
in total) showed continuous presence while the unit was on. So the SoC does
not run from VBUS alone; power-up happens when the switch is thrown, which is
when the `USB_KEY` dongle's key must already be present (docs/10 §6).
Switched back on at about 21:33: the unit re-enumerated with the same serial within the
few seconds it takes to boot and answered the identity query as `FM-1_015`
again. The USB cable stayed connected throughout, so the absence was the
device, not the link. Off period observed: 21:27:48 to at least 21:30:56
(`scratch/usb_monitor4.log`, 180 samples, all absent).

## 2. Identity query (docs/09 §3)

Tool: `tools/fm1_identify.py` (mido + python-rtmidi over CoreMIDI). Sent
`F0 00 32 45 00 00 00 40 7F F7` twice; both replies byte-identical:

```
F0 00 32 45 58 01 00 00 23 4D 5A 44 79 05 26 4C 1A 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 20 06 F7
```

Decoded (7-bit LSB-first unpacking of everything between `F0` and `F7`; the
`00 32 45 58` header is part of the stream and unpacks to `00 59 11`):

```
00 59 11 | 1B 00 00 | 46 4D 2D 31 5F 30 31 35 00×17 | 19        (34 bytes)
type 0x11  len 27     "FM-1_015" + zero padding        checksum ~sum OK
```

**The unit runs `FM-1_015` (V15).** Note for AL-255: the plain field carries
the whole `MODEL_NNN` identity; the second-field derivation in
`parse_handshake_identity` (bytes 14–33 plus ASCII `0`) evaluates to version
`0` on this real reply, so their "hardware validation pending" item resolves
as: parse the plain field.

| Sent | Result |

accepts DX7 dumps and parameter changes but has no read-back path over MIDI.

## 4. The macOS updater embeds V14, not V15

- `~/Downloads/M-UPGRADE-FM1.dmg` (59786679 B, downloaded 2026-09-06, volume
  `M-EFCS 1`) contains `M-UPGRADE-FM1.app` (bundle id `sinco.M-UPGRADE-FM1`,
  Qt 6 frameworks). Its universal binary (x86_64 + arm64, 2954528 B, sha256
  `db4048dc251c1afbec76c5ed64554b5b4a0950c9df97846a8b8ad709eb83acf2`) is
  byte-identical to the `M-UPGRADE-FM1.app` dated 2026-07-08 already in
  `~/Downloads`.
- `tools/extract_fwsc_from_updater.py` carved one package from file offset
  `0x47EB8`: 704052 B, sha256
  `a1adca99b1f9823ff2873292be74877a7a14ca0846fca3d25a23aba2750162d3` =
  AL-255's V14 package (`FM-1_014`) byte for byte; the unpack is identical to
  AL-255's `firmware-images/v14/raw_fw/FM-1.fwsc_unpack`.
- Consequence: running the stock macOS updater on this unit would **downgrade**
  it from V15 to V14 (stock downgrades are accepted, docs/03 §5).

**removed** `FM-1_014`, `Reset All Patches Turn the K4`, `Cancel Reset Turn
